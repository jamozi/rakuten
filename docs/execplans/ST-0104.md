# ST-0104 ExecPlan — Install contract repository

## 1. Story and outcome

- Story: `ST-0104`, `EPIC-01`, P0/M, MVP.
- Objective: install the OpenAPI, AsyncAPI, JSON Schema, AI, and Content
  contracts.
- Dependencies: `ST-0101`, `ST-0002`, `ST-0003`, and `ST-0004`; all four
  are locally implemented proposals while their canonical effective status
  remains unchanged.
- Required suite: `TST-002` (formal environment: CI).
- Acceptance criterion: every reference and declared hash resolves.
- Outcome: a versioned, immutable contract bundle, a deterministic installer,
  a fail-closed read-only loader, and a no-network integrity/reference gate.

Type/client generation, CI workflows, AI or Content runtime semantics, database
migration, provider integration, publication, and deployment are explicit
non-goals.

## 2. Context and source boundary

The canonical master/integration documents, decisions and Open Decisions,
ST-0104 backlog row and critical path, TST-002 definition and environment,
ST-0002/ST-0003/ST-0004 cumulative revision handoffs, ST-0101 workspace
contract, and current status overlay were reviewed. ST-0104 has no direct
requirement, design, security-control, threat, or Open-Decision identifier.

`changes/st-0004` is the sole installation source. Its manifest SHA-256 is
`5ba47a83548e6acfaa706ab4d3595cd05af39d9fa53fb411c17c44d7b478f458`.
It owns one `job-state.v1.yaml` and 305 files under `contracts/**`, including
244 JSON, 47 YAML, 12 Markdown, and two CSV payloads. It already incorporates
the ST-0002 and ST-0003 revisions; ST-0104 must not reconstruct or merge them.

The cumulative relative shape is significant. OpenAPI, AsyncAPI, and resource
catalog extensions refer to `../job-state.v1.yaml` or
`../../job-state.v1.yaml`. The installed layout is therefore:

```text
contracts/
  README.md                         # ST-0101 generated workspace marker
  raos-v0.4/
    contract-repository.v0.4.json  # ST-0104 generated ownership manifest
    job-state.v1.yaml              # byte-identical ST-0004 payload
    contracts/**                   # 305 byte-identical ST-0004 payloads
```

Flattening or rewriting the cumulative bundle would invalidate semantic
references and source hashes and is forbidden.

## 3. Invariants

- Canonical, upstream, ZIP, imported-manifest, and `changes/st-0004` inputs
  remain byte-for-byte unchanged.
- Every installed source payload is byte-identical to its pinned ST-0004
  manifest entry; the generated ownership manifest is the only added file
  inside the version root.
- Build and check reject traversal, absolute or backslash paths, case-fold
  collisions, symlinks, non-regular files, partial ownership, unknown files,
  missing files, size drift, and hash drift.
- The loader never fetches a remote resource and exposes only manifest-owned
  paths, registered schema IDs, or six explicitly reviewed retrieval aliases.
- The ownership manifest is a trusted loader input. Only the composite
  source-check plus verifier gate attests reconstruction from pinned ST-0004
  bytes.
- OpenAPI 3.1.1, AsyncAPI 3.0.0, and JSON Schema Draft 2020-12 remain the
  installed dialect/version contracts.
- AI/content loaders, activation, business validation, generated clients and
  types remain owned by later Stories.
- Local TST-002-equivalent evidence cannot become formal CI evidence and does
  not apply a canonical status transition.

## 4. Design

`scripts/build_st0104_contract_repository.py` verifies the pinned ST-0004
manifest and complete source inventory before writing. It renders a sibling
staging tree, copies all 306 payloads without transformation, emits a sorted
JSON ownership manifest, preserves the existing ST-0101 marker byte-for-byte,
fsyncs staged files/directories, and atomically exchanges only the owned
version tree with rollback via Linux `renameat2(RENAME_EXCHANGE)`.
`--check` regenerates independently and compares the complete installed tree
without writing.

`python/raos/shared/contract_repository.py` is a standard-library-only,
read-only loader. It strictly parses the ownership manifest, verifies exact
inventory/size/SHA-256 and safe filesystem shape, rechecks payloads when read,
parses JSON with duplicate-key rejection, and indexes unique top-level JSON
Schema `$id` values plus the exact six manifest-declared retrieval aliases. It
provides no semantic AI, content, HTTP, event, or provider behavior.

`scripts/verify_contract_repository.py` is the local TST-002-equivalent gate.
Using the already locked development tooling, it strictly parses contract
formats, validates JSON Schema dialect documents, and resolves every local
`$ref` target and JSON Pointer. It additionally resolves all 344 JSON Schema
references from each current `$id` base using a no-retrieval registry with 224
canonical resources and six explicit aliases, as permitted by JSON Schema
Core section 9.1.2. Exact official OpenAPI 3.1 and AsyncAPI 3.0
JSON Schemas are retained with their licenses under
`scripts/contract_validation_resources/`, checked against hard-coded SHA-256
pins, and used offline for complete document-structure validation. The gate
then classifies the frozen corpus by source role: 2,940 OpenAPI references
(492 Schema, 486 Parameter, 1,434 Response, and 528 Header) and 557 AsyncAPI
references (37 operation-channel, 249 operation-message, 144 channel-message,
22 channel-server, and 105 message-payload). Category namespaces, AsyncAPI
operation/channel membership, and non-schema Reference Object chains are
checked explicitly; wrong-category, cross-channel, and cyclic chains fail
closed. The 344 standalone JSON Schema references plus three references among
seven meta-validated embedded public-resource schemas complete role coverage
for all 3,844 physical `$ref` occurrences. A separate semantic pass requires
all 192 references to remain at their frozen document/JSON-Pointer locations,
all 99 schema-bearing catalog paths, and 12 prompt-frontmatter output paths to
resolve to standalone schema-document roots. Embedded YAML schemas are first
restricted to the JSON data model, including recursive string-only object
keys. Boolean OpenAPI component schemas
are accepted only at the exact component root, while boolean annotation fields
and unreviewed schema fragments are not treated as schemas. The gate
also checks schema registry ID/hash bindings, all internal declared hash
bindings, prompt frontmatter, and the bundle's declared local path and Schema
ID references. Schemes, remote fetches, bundle escape, missing dialects,
renamed inventory paths, and ambiguous IDs fail closed.

## 8. Risks and decisions

- Semantic path fields are broader than JSON Schema `$ref`. Only documented
  local contract-path fields are resolved; arbitrary business strings are not
  reinterpreted as paths.
- The installed source is an implementation candidate, not a canonical apply.
  Its provenance and proposal-execution prohibitions are retained unchanged.
- YAML and schema tooling remain development-only; the reusable loader is
  standard-library-only so ST-0104 does not create an undeclared application
  runtime dependency.
- The byte-frozen schemas contain six relative references whose canonical URI
  targets differ from target `$id` values. The generated ownership manifest
  records a closed six-entry retrieval alias contract; no alias is inferred
  from physical co-location and network retrieval remains forbidden.
- The two official specification schemas are treated as executable verifier
  inputs: their bytes, provenance, and licenses are repository-owned, and a
  hash mismatch fails before parsing. Updating either is an explicit reviewed
  contract change rather than an implicit network refresh.
- Strict full-tree ownership means downstream Stories must install generated
  outputs outside `contracts/raos-v0.4` or explicitly revise this contract.
- Formal CI, hosted clean-clone execution, human review, release, staging, and
  production remain unexecuted.
