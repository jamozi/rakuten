# ST-0202 ExecPlan - Local S3-compatible object service

## Story and outcome

- Story: `ST-0202`, `EPIC-02`, P0/S, MVP.
- Objective: provide local storage for Raw/Snapshot artifacts.
- Dependency: `ST-0102`.
- Deliverables: one S3-compatible service and bounded bucket bootstrap.
- Acceptance criterion: authenticated put/get/version fixture.
- Required suite: release-blocking `TST-014` in the canonical CI environment.
- Security controls: `SEC-DATA-003`, `SEC-DATA-004`, `SEC-DATA-008`,
  `SEC-INFRA-001`, `SEC-INFRA-006`, `SEC-SDLC-003`, and `SEC-SDLC-004`.
- Blocking policy input: `OD-014` remains `HUMAN_DECISION_REQUIRED`; its safe
  default disables automatic deletion and does not authorize a retention
  period or object lifecycle-delete policy.

The scoped outcome is a deterministic local/CI service candidate and an
authenticated artifact fixture boundary. It is not production infrastructure.
No image pull, service start, readiness probe, authenticated S3 operation,
container scan, or formal TST-014 result is claimed without real runtime
evidence.

## Preflight

1. Read the exact ST-0202 Story, its ST-0102 dependency, TST-014, OD-014, data
   classification, security controls, architecture design, and implementation
   handbook.
2. Preserve `zip/**`, `docs/canonical/**`, `docs/upstream/**`, and
   `docs/manifest.json` byte-for-byte.
3. Review current official SeaweedFS sources and resolve the 4.29 OCI index,
   linux/amd64 manifest, and image configuration separately.
4. Record the selected release's object-versioning and object-lock fixes as a
   runtime regression obligation, not as a passed test.
5. Keep the identity document out of environment values, process arguments,
   logs, and the repository. Move it only through the reviewed chain: host
   mode-0600 source, bootstrap Compose secret, non-persistent tmpfs UID 1000
   mode-0400 staged copy, then the official entrypoint running as UID 1000.
6. Keep the candidate private: loopback host binding, internal bridge, named
   volume, no host network, no privilege escalation, and no Docker socket.
7. Preserve the cumulative root Compose contract and the existing ST-0201
   PostgreSQL service.

## Invariants

- The exact image index, linux/amd64 manifest, and config digests are pinned.
- The service command disables master telemetry and all unneeded interfaces.
- `/status` and `/healthz` are readiness signals only; neither can satisfy the
  authenticated acceptance criterion.
- `raos-raw` is private, object-lock-capable at creation, and versioned.
- Accepted artifacts round-trip `sha256`, `content-type`, `source`,
  `acquired-at`, and `retention-class`; a body/hash mismatch is rejected.
- `OD-014` is not resolved locally. Default retention and lifecycle deletion
  are forbidden, and automatic deletion remains disabled.
- Effective canonical Story and suite status remain unchanged until governed
  status evidence is reviewed.

## Implementation

1. Define `changes/st-0202/contracts/local-object-storage.v1.yaml` as the
   semantic source for image, Compose, runtime/bucket acceptance, security
   controls, OD-014 handling, and verification limits.
2. Extend `scripts/build_local_compose.py`, the only root Compose writer, with
   strict ST-0202 validation and deterministic cumulative rendering.
3. Generate the cumulative `docker-compose.yml` and the active Story manifest
   with source/generator/command provenance and predecessor-chain integrity.
4. Implement `scripts/object_storage_service.sh` with a fixed local Docker
   socket, fixed local project, file-secret validation, exact Compose-service
   and image/platform checks, bootstrap-secret to non-persistent-tmpfs staging,
   UID 1000 execution, readiness-only probing, and an isolated disposable test
   project.
5. Implement `scripts/object_storage_fixture.py` so acceptance performs
   authenticated bucket creation, versioning, versioned put/get, required
   metadata round-trip, SHA-256 mismatch rejection, and retention-hook checks
   without creating a retention period or lifecycle-delete rule.
6. Test positive semantics and negative mutations for image identity, secret
   transport, command hardening, networking, bucket policy, OD-014, status
   promotion, and readiness/acceptance separation.
7. Integrate dedicated Storage CI/governance surfaces without conflating them
   with the Database check or claiming formal TST-014 execution.

## Verification commands

```bash
uv run --locked --no-sync python scripts/build_local_compose.py
uv run --locked --no-sync python scripts/build_local_compose.py --check
bash -n scripts/object_storage_service.sh
uv run --locked --no-sync pytest -p no:cacheprovider -q tests/st0202
```

A real runtime smoke additionally requires an available local Docker Engine
and Compose plugin. It must execute the authenticated fixture and produce
reviewable evidence before any runtime PASS can be recorded.

## Completion boundary

Local generation and focused tests can establish an implementation candidate;
they cannot change the effective canonical `NOT_STARTED / NOT_EXECUTED` status.
Formal TST-014 remains `NOT_EXECUTED` until canonical CI runs the complete
hash/version/tamper/retention-hook suite with reviewed evidence. The container
vulnerability scan and the SeaweedFS 4.29 object-lock/version-delete regression
also remain mandatory runtime gates.
