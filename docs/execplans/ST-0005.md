# ST-0005 ExecPlan — Status registry workflow

## 1. Story and outcome

- Story: `ST-0005`, `EPIC-00`, P0/M.
- Requirement: `FR-020`.
- Design: `RAOS-STATUS-TAXONOMY-001`.
- Dependency: `ST-0001`.
- Outcome: a deterministic status validator, operational overlay, transition
  request contract, and narrow PR check that reject invalid promotion.
- Non-goals: open-decision gating (`ST-0006`), toolchain/base CI (`ST-0102`,
  `ST-0106`), PR governance (`ST-0107`), and Gate packs (`ST-1607`).

## 2. Context read

The implementation reads the Master README, canonical Integration design,
Canonical Decisions, Open Decisions, Story row, Status Taxonomy, aggregate
Registry, Test Suite catalog, repository/canonical AGENTS and PLANS, ST-0001
importer, ST-0001 through ST-0004 work logs, and ST-0004 generation safety
patterns.

The immutable v1.0 base remains authoritative. `docs/manifest.json` and the
four status inputs are SHA-256 pinned. The complete ST-0001 imported file set
is reverified before generation or request validation.

## 3. Invariants

- No canonical/upstream/ZIP artifact is edited.
- A local result is never represented as formal CI/runtime `PASS`.
- A proposal changes exactly one Story, carries no governance fields, and
  never changes effective status.
- Unknown fields, statuses, Stories, Suites, environments, and evidence
  classes fail closed.
- Every Story retains its complete-base digest, required Suites, unresolved
  decisions, and canonical source status; only `APPLY` changes effective
  status fields.
- Effective updates use optimistic base and row status checks.
- Forward `VALIDATED`/deployment pairs require verification `PASS`. Deployment
  implementation transitions remain grammar declarations blocked pending
  typed gates; a verification-only transition does not change implementation.
- AI/automation cannot approve, self-approval is impossible, and
  `VALIDATED`/production requests are human-only.
- Evidence is repository-local, path-safe, non-symlink, and hash-bound.
- Every snapshot is bound to its Story, class, Suite, environment, result,
  recorded time, and formal status. Replay uses immutable content-addressed
  captures; a newly introduced live snapshot must also match its regular,
  repository-local original. Orphan snapshots and captures fail.
- Every capture digest identifies exactly one artifact file. `APPLY` evidence
  identity is atomic and single-use per Story/Suite/class/capture, so
  overlapping or superset capture sets do not reuse an already-consumed
  identity.
- Each concrete PR URI, PR changeset identity, and immutable approval artifact
  is globally single-use for `APPLY`. Production identity is
  Story/governance-role/artifact-SHA; scope identity is Story/artifact-SHA, so
  genuine cross-Story batch governance remains possible. A request's scope
  artifact must be separate from its approval artifact.
- Requests and evidence snapshots are append-only; corrections add history.
  Modify/delete/rename enforcement is owned by the base PR workflow.
- Explicit strict-UTC requested/observed/expiry/decision times provide
  who/when/what/why auditability and stale-evidence rejection. Explicit null
  temporal/governance values fail closed. Every APPLY evidence item remains
  valid through the human approval decision; later status-changing evidence
  strictly postdates both the active observation and the latest applied
  approval decision for that Story. Expiry may equal but never precede its
  captured validity boundary, must invalidate the exact active evidence set,
  and may not be requested or observed before `valid_until`. Historical
  offline replay is wall-clock independent, while live validation rejects
  wall-clock-future request/observation/decision timestamps and evidence
  expired at the live reference. A future expiry boundary remains valid while
  evidence is fresh.
- Verification `PASS` uses the exact required-Suite set; PARTIAL, FAIL,
  regression, expiry, and demotion use a nonempty required-Suite subset.
- Scope transitions require a human requester, PR, distinct human approver,
  and separate scope-authority artifact. Production promotion requires four
  distinct artifacts for release decision, Gate, security, and operations.
- Public/content/finance/editorial data and publication behavior are not
  touched.

## 4. Proposed design

`scripts/build_st0005_status.py` verifies the immutable base, validates sorted
requests, builds an overlay for 129 Stories/32 Suites/six environments, and
atomically installs only its generated ownership. `PROPOSE` stores pending
history without changing effective status fields. The offline validator models
the full structural grammar and replays committed non-deployment `APPLY`
history only after concrete GitHub PR metadata, an implementation commit that
precedes the request-bearing PR head, and distinct human approval pass
structural validation. New authoritative live `APPLY` requests remain
fail-closed until `ST-0006` open-decision gates and `ST-0107` authenticated
review governance are integrated. Implementation transitions involving a
deployed status remain blocked offline and live until `ST-1505`, `ST-1506`,
and `ST-1607` provide typed gates; verification-only changes while deployed are
not deployment implementation transitions.

The request JSON Schema is strict Draft 2020-12. Manual validation adds
cross-document checks that JSON Schema alone cannot express: exact Suite set,
Suite/environment/evidence-class compatibility, evidence file hashes, base
and row concurrency, authority separation, and verification/implementation
coupling, time ordering/expiry, nonempty subset failure evidence, complete
PASS evidence, exact snapshot identity/result binding, live source-artifact
path/hash verification when a capture is introduced, immutable-capture replay,
global PR/approval identity consumption, Story-scoped production/scope
identities, separate scope/approval artifacts, exact expiry invalidation, four
distinct production-governance artifacts, and a no-orphan append-only
snapshot/capture inventory.

Generation occurs in sibling staging. Ownership and manifest verification run
before replacement. A failed render cannot modify the prior tree; a failed
install restores it.

The base-owned `pull_request_target` workflow pins checkout to a full commit,
checks out the exact head, and fetches ancestry. Before any Python process, a
shell-only guard rejects status-history changes combined with trust-surface
changes and restores the complete `scripts/` tree from the exact base SHA.
Candidate-head Python therefore cannot be imported; the candidate supplies
data only. The workflow replays history offline, binds only added requests to
the live PR, and rejects existing request/evidence M/D/R operations. The
future `APPLY` handoff is two commits: implementation commit A, then
request-bearing commit B; the workflow proves A is an ancestor of B before the
current fail-closed activation gate rejects the new `APPLY`. It assumes an
existing Python/PyYAML environment, installs no unowned toolchain, and does
not claim to be the deferred base CI.

## 6. Test plan

All local checks map to the static intent of `TST-001`, but not its formal CI
execution. Tests cover canonical counts/digests, strict schema validation,
proposal non-effect, unknown field/status/Story/Suite rejection, evidence
path/symlink/missing/hash rejection, required-Suite mismatch, lost updates,
forward/demotion policy, regression/expiry behavior, `PASS`/`VALIDATED`
coupling, automation/self-approval rejection, PR-context mismatch,
timestamp/expiry ordering, deferred/out-of-scope transitions, append-only
history, approval-time freshness and per-Story decision watermarks, global
PR/approval reuse rejection, snapshot relabel/reuse rejection within the same atomic
Story/Suite/class/capture binding,
snapshot-source escape/missing/symlink/hash rejection, orphan rejection,
determinism, drift, ownership, and failure-atomic replacement.

## 7. Evidence plan

The manifest pins every source and generated payload artifact. The manifest
itself is intentionally excluded from its own inventory and verified through
deterministic byte comparison. Local pytest, Ruff, Pyright, `py_compile`,
importer verification, build, and `--check` results are recorded in the work
log. No evidence is pre-marked as formal `TST-001` PASS.

## 8. Risks and decisions

- There is no usable Git repository/PR, so initial records are proposals only.
- Local `LOCAL` is operational evidence metadata, not a canonical runtime
  environment.
- Request approval metadata is structurally enforced, but a new authoritative
  live `APPLY` is rejected until `ST-0006` and `ST-0107` provide the missing
  decision and authenticated-review gates.
- The workflow cannot pin Python dependencies before the toolchain stories;
  it fails on a missing prerequisite instead of downloading an implicit one.
