# ST-0106 ExecPlan — Base pull-request CI

## 1. Story and outcome

- Story: `ST-0106`, `EPIC-01`, P0/M, MVP.
- Objective: run lint, type, contract, unit, and secret checks on every pull
  request.
- Dependencies: `ST-0102`, `ST-0103`, and `ST-0104`.
- Required suites: `TST-001` and `TST-002` (formal environment: CI).
- Acceptance criterion: every required job has an equivalent local command.
- Design reference: `RAOS-SEC-001`.

The Story installs a read-only GitHub Actions workflow and deterministic local
job entrypoints. GitHub setup/checkout and source-constrained dependency
hydration are the only network-enabled phase; repository checks execute only
after a fail-closed transition into fresh user, network, and PID namespaces
with an inherited socket-denial filter. Branch rules,
CODEOWNERS, deployment, OIDC, release artifacts, SBOM/provenance, PostgreSQL
services, and any provider credential are later Story scope.

## 2. Context and decisions

The canonical backlog row, TST-001/TST-002 definitions, security design,
SDLC controls, threat register, repository toolchain wrappers, and the existing
status-registry workflow were reviewed. ST-0106 has no Open Decision.

GitHub's current official guidance was checked on 2026-08-02. Actions are
pinned to full commit SHAs, `GITHUB_TOKEN` receives only `contents: read`,
checkout does not persist credentials, pull-request code receives no secrets or
write permission, and every job has a timeout. Setup caches are disabled so an
untrusted pull request cannot publish reusable default-branch cache state.
The reviewed source URLs are recorded in
`docs/architecture/ST-0106-github-actions-snapshot.yaml`, including GitHub's
secure-use and workflow-syntax guidance, each setup action's official
repository, and the `ubuntu-24.04` hosted-runner image definition.

## 3. Invariants

- CI executes the pull-request tree through the unprivileged `pull_request`
  event, never `pull_request_target`.
- No job receives a repository/environment secret, cloud credential, OIDC
  token, write permission, deployment environment, or production data.
- Every external action uses one reviewed full-length commit SHA.
- Exact ST-0102/ST-0103 tool versions and lockfiles remain the build inputs.
- Before hydration, a network-denied, process-isolated validator rejects any
  dependency input that is not exactly pinned, integrity bearing, and sourced
  from the approved PyPI/pythonhosted or npm registry origins.
- The validator and its hostile test fixture use the workflow's stable
  `/usr/bin/python3 -I` system interpreter path. They do not require a
  version-specific system-Python executable that a later hosted-runner image
  may not provide.
- The npm lock validator accepts only positive ASCII semver descriptors. Every
  root/workspace dependency and nearest transitive dependency resolves to a
  captured entry whose version satisfies the effective descriptor; only an
  explicitly optional peer may be absent. The exact ST-0103 overrides are a
  closed contract and the only descriptor substitutions.
- After exact Node setup but before registry-enabled npm hydration, bundled npm
  resolves a disposable metadata-only copy with a fresh empty cache under the
  denied-network guard using `ci --dry-run --offline`. The copied lock remains
  byte-identical and no `node_modules` path may be created.
- GitHub setup/checkout and source-constrained locked dependency hydration are
  the only network-enabled phase. Hydration directly invokes pinned setup
  tools with `uv --no-config --no-build --no-sources` and npm
  `--ignore-scripts`; it executes no repository Make target, wrapper, or
  package lifecycle/build hook.
- CI starts the documented repository job wrapper from inside
  `scripts/run_network_denied.sh`. A direct local wrapper invocation enters the
  same boundary itself after a separate local hydration command.
- The isolation guard rejects a root caller and maps the current non-root
  identity into the child namespace; repository tests must not gain
  namespace-root capabilities as a side effect of denying the network.
- On Ubuntu hosts that reject the fixed unprivileged current-user namespace
  probe, the guard may use only the owner-approved fixed
  sudo -> env -> unshare -> setpriv compatibility chain. Root creates fresh
  network/PID/mount namespaces, but setpriv restores the original non-root
  UID/GID, clears supplementary groups, drops every capability set, and fixes
  no_new_privs before the repository assertion or requested command runs. The
  wrapper must never change a sysctl or AppArmor policy.
- The isolation wrapper rejects socket standard descriptors, closes all other
  inherited descriptors through a kernel range close that is independent of
  caller-controlled resource limits, isolates and kills the child PID
  namespace, and prevents hydration/preflight descendants from crossing phase
  boundaries.
- `scripts/assert_network_denied.py` must fail closed unless the child network
  and PID namespaces differ from their parents, exposes only loopback, has no
  usable IPv4 or IPv6 external route, and inherits `no_new_privs` plus the
  socket/connect/bind/listen/accept/io_uring seccomp deny policy. Local
  `socketpair` remains allowed for tool signalling.
- The secret scanner runs through the same denied-network wrapper; direct
  `--worktree` execution is diagnostic only.
- Secret findings report only source location and rule identifier, never the
  matched credential value.
- Secret scanning covers maintained worktree files, nested ZIP artifacts, and
  every fetched Git blob; a shallow or absent history fails the CI history
  mode.
- Canonical, upstream, ZIP, generated contract, and prior evidence artifacts
  remain immutable.
- A local or hosted run cannot change effective canonical status by itself.

## 4. Planned implementation

- Add `.github/workflows/ci.yml` with independent `static`, `unit`,
  `contracts`, and `secrets` required-job candidates.
- Add a hardened exact-tool `scripts/ci_job.sh` wrapper and matching Make
  targets for the first three jobs, with dependency hydration separated from
  the repository-check phase.
- Add a standard-library `scripts/validate_ci_hydration.py` preflight for
  exact pins, approved origins, integrity metadata, safe npm configuration,
  dependency closure, and captured-version range satisfaction.
- Add an exact npm offline dry-run after setup-node and before network-enabled
  hydration to verify npm's own peer, override, and resolution semantics in a
  disposable metadata-only copy.
- Add `scripts/run_network_denied.sh` and
  `scripts/assert_network_denied.py` to create and attest a fresh route-less
  user/network/PID namespace before repository-owned checks execute.
- Add a standard-library `scripts/scan_secrets.py` scanner for the worktree,
  Git object history, and bounded nested ZIP inspection.
- Add isolated `tests/st0106/**` contract, wrapper, and malicious-fixture tests.
- Record the official-source action snapshot and update README/commands in the
  same pass.
- After all gates pass, append ST-0106 evidence/request data through the
  ST-0005 generator without editing canonical status.

## 5. Verification plan

- Parse and structurally validate the workflow, action pins, triggers,
  permissions, runner, timeouts, and exact local commands.
- Exercise the wrapper with exact real tools and adversarial fake tools,
  inherited environment inputs, symlinked paths, and unsupported commands.
- Prove the workflow hydration runs direct fixed `uv`/npm commands without
  repository code, builds, source overrides, or lifecycle scripts. Prove every
  repository target reasserts the denied-network state. Reject execution in
  the parent namespaces, with a non-loopback interface, or with an external
  route.
- Mutate transitive descriptors, required/optional peers, root/workspace
  closure, workspace links, and the exact override contract. Require both the
  standard-library validator and the exact npm empty-cache offline preflight to
  reject resolution that would need an uncaptured registry artifact.
- Reject inherited connected descriptors and pathname Unix sockets; prove a
  preflight background descendant is killed while local `socketpair` remains
  usable by the locked tools. Include a connected descriptor above a lowered
  soft file-descriptor limit so the closure proof cannot depend on mutable
  `RLIMIT_NOFILE`.
- Reject unknown launch modes, unsafe privileged-helper ownership/mode,
  unavailable noninteractive sudo, a reused fallback mount namespace,
  supplementary groups, and any nonzero inheritable, permitted, effective,
  bounding, or ambient capability after the fallback drop. Prove the fixed
  privileged argv reaches setpriv before a repository path.
- Run those parent-side guard probes directly with no delegated cases. In the
  already-denied unit job, delegate only the probes that require creating a
  nested namespace or parent socket, and fail the suite unless an
  always-collected assertion revalidates the real outer namespace,
  non-root identity, `no_new_privs`, and seccomp state. These include the
  root-mapped child-namespace and root-mapped wrapper-caller rejection probes;
  both still execute and must reject in the direct unsandboxed suite.
- Detect representative AWS, GitHub, OpenAI, PEM, and generic credential
  forms without echoing their values.
- Detect a credential deleted from the current tree but retained in Git
  history, and a credential inside a nested ZIP.
- Reject archive traversal, encryption, excessive expansion, unsafe symlinks,
  truncated history, unreadable inputs, and unknown worktree entries.
- Run all four local job equivalents, isolated ST-0106 tests, predecessor
  gates, ST-0005 capture/bundle checks, and a protected-input hash audit.
- Run the exact full-history local secret equivalent through the isolation
  guard:

  ```bash
  scripts/run_network_denied.sh --home "$HOME" -- \
    /usr/bin/python3 -I scripts/scan_secrets.py --worktree --git-history
  ```

- Treat hosted GitHub execution as `NOT_EXECUTED` until a real workflow run
  exists.
- On a real GitHub-hosted ubuntu-24.04 pull-request run, require Static, Unit,
  Contracts, and Secrets to report PRIVILEGED_NAMESPACE_THEN_DROP and pass
  their unchanged repository checks. The local host has no passwordless sudo,
  so local fallback runtime evidence remains
  NOT_EXECUTED_PASSWORDLESS_SUDO_UNAVAILABLE.

## 6. Completion boundary

Local completion requires all job equivalents and regression gates to pass,
an independent audit to find no unresolved material issue, and append-only
status evidence to validate. Formal TST-001/TST-002 and effective canonical
status remain unchanged until a reviewed GitHub run and status transition are
applied.

## 7. Owner-approved V2 cache, reviewed-findings candidate, and activation

The exact V2 handoff at SHA-256
`88a6d97cd70728c860ed7ab1b600d0c8cc69239a48a43d5c1b0c82919ff86e0c`
authorizes a direct repository-local candidate only. The implementation has
two independently gated parts.

For Unit, the workflow creates exactly one fresh mode-`0700` uv cache below
`RUNNER_TEMP` before the network-enabled locked sync. The sync keeps the exact
Python version, PyPI origin, first-index strategy, disabled keyring,
no-build/no-sources rules, prerelease policy, and exclude-newer boundary. It
removes `--no-cache` only when that explicit job cache is bound. The denied
network phase receives the cache and runner root only as `ci_job.sh` arguments;
ambient cache or runner variables are removed. Unit requires this extended
form, while Static and Contracts reject it and preserve their seven-argument
form. Make receives only the canonical cache path as
`RAOS_CI_UV_CACHE_DIR`. A fresh-project `uv sync --locked --offline` probe must
succeed from that exact cache; lock resolution alone is insufficient.
After that proof, a deliberate `pyproject.toml` drift probe accepts only uv
0.12.1's two fail-closed outcomes: a direct stale-lock diagnostic, or the
closed cache-only resolver refusal stating that the network is disabled and a
registry package is unavailable in the cache. The latter is expected because
`sync --locked` populates the distributions needed to rebuild the exact lock,
not every registry metadata response needed to resolve a changed project. An
empty or incomplete explicit cache still fails before any drift assertion.

Unit also creates exactly one fresh mode-`0700` npm cache at the physical
repository path `$GITHUB_WORKSPACE/.npm-cache`, rejecting both an existing path
and a symlink and verifying the runner UID/GID and mode before the direct
pinned npm hydration. That path is the existing ST-0103 wrapper cache, so the
subsequent denied-network Unit phase can run its nested wrapper syncs and
fresh offline reconstruction without registry access. Static and Contracts
retain their isolated runner-temporary npm caches. This does not add a
persistent or cross-job Actions cache.

For Secrets, `--reviewed-findings` remains an optional input. Its absence
preserves the original result and sanitized output. Its strict, bounded,
descriptor-safe JSON-compatible YAML ledger rejects unsafe paths, symlinks,
non-regular files, duplicate keys or entries, YAML alias/anchor/tag/merge
syntax, unknown fields or rules, wildcards, prefixes, traversal, unsafe sizes,
stale worktree entries, and source or line drift. Only exact
`GENERIC_CREDENTIAL` members are subtracted after scanning. A specific finding
at the same source and line remains a finding. The ledger has no generator or
self-approval path and cannot contain matched values.

The direct candidate ledger binds the reconciled 31 worktree and 58 Git blob
locations observed for run `31821288195`. Its immutable internal marker remains
`UNAPPROVED_CANDIDATE`; the frozen candidate is 46,295 bytes at SHA-256
`1038cf6ef81da0acab528cf8206086646b6e003f5ac0ceed4f2e4b994827bcc7`.
A plausible real credential would have stopped ledger construction and entered
incident handling without recording the value. Sanitized per-location review
instead covered all 89 entries, reproduced the 31/58 scopes exactly, found no
specific-rule finding, and identified no plausible live-credential incident
candidate.

The repository owner then approved that exact candidate and its exact CI
reference within the existing V2 stop conditions. The detached activation
record `changes/st-0106/REVIEWED-SECRET-FINDINGS-APPROVAL-v1.yaml` is 5,524
bytes at SHA-256
`b683ae3b3b7312bd4ce04fe2c796f1157542f72c1b1bca79919a71b3a7c1acd9`.
It binds the ledger, the sanitized review, the V2 handoff and handoff approval,
and the owner statement without changing the ledger. The permitted workflow
delta is only the appended argument
`--reviewed-findings changes/st-0106/contracts/reviewed-secret-findings.v1.yaml`
in the existing Secrets reproduction command. The scanner, Unit cache,
Static, Contracts, database, storage, and denied-network semantics are not part
of the activation delta.

The later ST-0107/downstream fixed-point provenance cut, hosted CI, formal
TST-001/TST-002 evidence, status or canonical mutation, staging, commit, push,
pull request, merge, external write, release, and Production remain outside
this plan and separately gated.

The exact handoff and detached approval files remain immutable audit and
allowlist records for the reviewed cache and secret-finding contracts. Their
historical approval-state fields are not a current permission checkpoint. The
repository owner's standing development authorization independently permits
reversible local implementation, tests, documentation, and an atomic Story
commit. It does not authorize push, pull request, merge, hosted evidence,
status transition, staging, external writes, release, or Production.

The additional direct checks are:

- wrapper rejection for missing, relative, non-directory, symlinked,
  noncanonical, unsafe-mode, wrong-owner, outside-runner-root, and ambient
  cache inputs;
- an incomplete explicit cache failing a real locked offline-sync probe rather
  than skipping;
- reviewed-ledger schema, duplicate, alias, merge, tag, stale, hash, line,
  worktree, Git-present, Git-absent, new-generic, and specific-rule hostile
  cases;
- exact 89-location candidate reproduction with no matched bytes in ledger or
  output, plus detached-approval byte/hash and exact workflow-command binding;
- isolated ST-0102/ST-0106 suites, focused static/type/parse checks, workspace
  drift, canonical import verification, exact changed-path secret scan,
  protected-byte audit, and `git diff --check`.
