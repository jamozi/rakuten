## 4. Proposed design

### Generation and migration

`scripts/build_st0303_iam_ops.py` is the sole writer for the next Alembic
revision, generated catalog, validation SQL, and manifest. It validates strict
YAML, exact source hashes, the predecessor digest, the normalization allowlist,
and the complete structured inventory before rendering. Installation stages
the complete bundle and keeps the manifest last; `--check` is read-only.

The revision creates tables and local constraints, installs the 20 available
foreign keys, indexes, functions, triggers, comments, and explicit PUBLIC
revocations. It neither creates roles nor grants workload access. The runtime
catalog advances only after the generated revision hash is fixed, and the
runner validates the installed ST-0303 shape in addition to the retained
foundation envelope.

### Behavior and boundaries

Job and Principal touch triggers update timestamps and monotonic lock versions
only for changed rows. The two hard-immutable registries use a normal-invoker
trigger guarded by both maintenance intent and migrator membership. Outbox
events participate in the caller transaction; Inbox and Idempotency unique
keys enforce duplicate rejection at the database boundary.

The generated validation artifact is no-write. Behavioral mutation probes run
only in disposable PostgreSQL 18.4 pytest databases and transactions.

## 8. Risks and decisions

- Risk: exact physical parity is broad. Mitigation: compare the full structured
  contract against a separately normalized pinned-source oracle, not counts
  alone.
- Risk: destructive downgrade may partially remove the slice. Mitigation:
  fixed-order all-table locks and one preflight before any drop, with one
  transaction and `RESTRICT` only.
- Risk: an owner could accidentally bypass immutability. Mitigation: test the
  four combinations of maintenance GUC and migrator membership.
- Decision: retain canonical NULL and break-glass limitations exactly; any
  strengthening requires a separately approved design handoff.
- Risk: this workspace has no valid Git repository, so formal PR and migration-
  owner approval cannot be produced locally.
