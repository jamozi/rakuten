# ST-0004 ExecPlan - Apply content canonical revision

## 1. Story and outcome

- Story ID: `ST-0004`
- Epic: `EPIC-00`
- Requirements: `FR-007`, `FR-010`
- Formal canonical decision: `INT-DEC-005`
- Supporting decision: `INT-DEC-006` (structured Content Repository is the
  authority; CMS is a publication adapter)
- Required suites: `TST-002`, `TST-003`, `TST-008`, `TST-020`
- Outcome: consume the hash-pinned ST-0003 v0.3 candidate and immutable
  RAOS-CONTENT-001 package to produce a self-contained v0.4 revision. The
  revision adopts Content AST, Article Type, Recommendation Methodology, SEO,
  Disclosure, Media, and Publication Manifest as formal DB/Admin/Internal
  API/AI contracts, and preserves five valid plus 15 invalid article fixtures
  as deterministic content-policy evidence.

Explicit non-goals:

- installing the final contract repository or generating language clients
  (`ST-0104`, `ST-0105`);
- implementing the migration runner/history/advisory-lock ABI (`ST-0301`);
- installing all domain schemas, grants, repositories, or application handlers
  (`ST-0304` through `ST-0308`);
- implementing the source-packet, Claim/Evidence, AI registry, Content AST,
  editorial, rendering, review, publication, or rollback runtimes
  (`ST-0604` onward);
- introducing new content events or changing the public API/read model;
- navigating or writing a CMS, creating a WordPress draft, publishing content,
  invoking an external provider, using production credentials, or changing a
  production database;
- changing the canonical aggregate Registry before ST-0005.

## 3. Invariants

- Supporting decision `INT-DEC-006` makes RAOS's structured Content Repository
  authoritative; a CMS is only a publication adapter and cannot become the
  content source of truth.
- Every publish, unpublish, rollback, approval, methodology override, and
  Claim/Recommendation change remains a human-authorized operation owned by a
  later story. AI and the generator cannot approve or publish.
- Content is a versioned structured AST. Raw HTML, arbitrary Markdown escape
  hatches, scripts, iframes, styles, and event handlers are forbidden.
- Only registered Block types are accepted. Unknown fields and unknown Block
  types fail closed at every contract trust boundary.
- Every major Claim is evidence-bound. Unknown, conflicting, missing, or stale
  facts are never guessed; they remain visible or safely degrade.
- Rakuten review bodies are never collected, stored, transformed, summarized,
  quoted, or used as fixture/evidence. Aggregate ratings cannot be converted
  into fabricated qualitative experience.
- First-hand experience claims require an immutable approved experience record;
  no fixture or AI output may fabricate use or testing.
- Recommendation methodology is versioned and excludes affiliate rate, reward,
  EPC, RPM, revenue, and profit inputs. Editorial and finance signals remain
  separate.
- Affiliate URLs are renderer-owned references resolved from approved offers;
  they are not free text in the AST, AI input/output, or editor-controlled
  body. Disclosure is renderer-owned, non-removable, and appears at the top.
- Structured data is deterministic from visible approved content and cannot
  invent Review, AggregateRating, Offer, Product, or FAQPage claims.
- Existing ST-0003 schemas, security objects, operations, events, and Job-state
  semantics remain intact. Job-state is copied byte-for-byte.
- AsyncAPI adds no channel, operation, message, event type, or event schema and
  declares `x-raos-wire-change: NONE`.
- Public OpenAPI remains byte-identical to the immutable v0.1 contract with
  SHA-256
  `8122958e80e04096ba3b254b4a8d843138bb757c8fc4e71bd8406914dba80797`.
  No content/evidence/editorial/AI/finance internal is publicly exposed.
- Proposal-only SQL/YAML is hash-pinned provenance and is never executed,
  copied into a migration, or treated as runtime configuration.
- Database changes use bounded, resumable Expand-Migrate-Contract checkpoints.
  Migration never guesses a content version binding and never holds a metadata
  lock across a table scan or concurrent-index build.
- Canonical/upstream evidence and aggregate status files remain byte-identical.
  Before ST-0005, implementation state is proposed only in the work log.

## 4. Proposed design

### Modules and ownership

- `changes/st-0004/database/` contains six formal versioned SQL checkpoints and
  forward-recovery guidance for the future ST-0301 runner.
- `changes/st-0004/contracts/` is a generated self-contained v0.4 candidate. It
  starts from the verified ST-0003 tree, promotes the seven root contracts and
  catalogs to v0.4, and adds frozen RAOS-CONTENT-001 contracts plus generated
  DB/API/AI resource and request schemas.
- `changes/st-0004/contracts/content/` contains 77 frozen artifacts: 18
  top-level files, 33 schemas, five templates, and 21 fixture-area files (five
  valid JSON, 15 invalid JSON, and `fixtures/invalid/expected_results.yaml`),
  plus generated canonical adoption metadata outside that frozen count.
- `scripts/build_st0004_revision.py` verifies every predecessor artifact,
  package checksum, proposal copy, and immutable input hash; renders in sibling
  staging; and installs only the owned complete generated tree.
- `tests/st0004/` owns deterministic generation, compatibility, references,
  fixture validation, API/event/public-isolation, static migration, and
  PostgreSQL migration checks.
- `docs/execplans/ST-0004.md`, `docs/worklogs/ST-0004.md`, and
  `changes/st-0004/README.md` record planning, evidence, ownership, and status
  boundaries. They are not generated contract artifacts.

The bundle manifest records nine source artifacts: the generator, README, six
SQL checkpoints, and forward-recovery guidance. Generated ownership includes
`job-state.v1.yaml`, `contracts/**`, and `manifest.yaml`. The generated artifact
count is derived from the final owned tree and is not hard-coded in this plan.

### Data and transaction boundaries

The SQL delta defines 11 database tables. Its payload is split into
independently recorded checkpoints:

1. `202607300013_content_expand.sql`: atomically add content schema/type/template,
   methodology/binding, SEO, structured-data, media, experience, disclosure,
   and supporting resources; add only nullable predecessor bindings; install
   migration-window integrity guards and fail-closed ACLs.
2. `202607300014_content_expand_validate.sql`: verify prerequisite definitions,
   validate safe constraints after Expand releases metadata locks, build exact
   side-by-side indexes with `CREATE INDEX CONCURRENTLY`, and perform exact
   postflight definition checks.
3. `202607300015_content_migrate_batch.sql`: process at most 1,000 automatic
   rows per transaction. Derive only hash/version bindings that are uniquely
   supported by stored evidence. Report unresolved/operator-bound rows in
   `remaining_rows`; never invent article type, methodology, SEO, disclosure,
   or publication-manifest identity.
4. `202607300016_content_contract_prepare.sql`: require an exact readiness
   report, verify canonical-compatible writer behavior, and install `NOT VALID`
   required-field constraints so new writes fail closed while existing rows
   remain available for validation.
5. `202607300017_content_contract.sql`: validate prepared constraints outside
   the short metadata transaction, then finalize canonical names/indexes,
   nullability, and predecessor compatibility without rewriting content rows.
6. `202607300018_content_guarded_downgrade.sql`: run only after explicit
   operator request. Refuse non-empty canonical-only resources, lossy bindings,
   approval/evidence/publication provenance, or any shape that cannot return
   exactly to post-ST-0003. A refusal requires forward recovery.

The migration runner, history schema, advisory-lock ABI, and deployment
orchestration remain ST-0301 ownership. Files are never concatenated into one
transaction.

### API, event, job, and type changes

- Promote `openapi-admin.v0.3.yaml`, `openapi-internal.v0.3.yaml`,
  `asyncapi.v0.3.yaml`, and the four v0.3 job/resource/schema/state catalogs to
  v0.4 revision metadata while preserving every predecessor surface.
- Add ten API resources and ten commands through 19 operations: 15 Admin
  operations `ED-016` through `ED-030` and four Internal operations `INT-005`
  through `INT-008`. Commands require Idempotency-Key; mutable updates require
  If-Match and return ETag; errors use RFC 9457 Problem Details; resource/action
  scopes remain least-privilege and auditable.
- Preserve all existing AsyncAPI channels, operations, messages, and schemas
  wire-equal. Add no content event without an explicitly designed consumer.
- Keep the public OpenAPI byte-identical and exclude raw AST internals, source
  packets, review data, evidence internals, AI artifacts, and finance fields.
- Add strict portable content resource/request schemas and registry entries
  without changing frozen RAOS_06 schema IDs or hashes.
- Add versioned content bindings for AIT-002, AIT-003, AIT-004, AIT-005,
  AIT-006, AIT-008, AIT-009, and AIT-010. Enforce allowed AST Blocks, evidence
  requirements, methodology/SEO/policy inputs, renderer-owned fields, finance
  exclusion, and finding-only authority without mutating frozen RAOS_05 files.
- Carry Job-state byte-identically; ST-0004 introduces no new Job state or
  lifecycle transition.

### Failure and rollback behavior

- Any manifest owner/version, predecessor artifact, input hash, archive member,
  checksum, proposal-copy, path, ref, schema, or fixture mismatch aborts before
  committed generated output is replaced.
- The builder refuses custom output, symlinked/unowned destinations, and
  unexpected generated files. A failed staged install restores the previous
  complete owned tree.
- Compatibility checks fail on removed operations/schemas, new required legacy
  fields, narrowed enums/types, changed event wires, changed Job-state bytes,
  or any public OpenAPI drift.
- Content validation rejects all 15 invalid fixtures and any mutation that
  bypasses disclosure, evidence, methodology, product identity, renderer
  ownership, or structured-data restrictions.
- Migrate/Contract checkpoints stop on ambiguous bindings or readiness drift.
  No operator may clear the backlog by deleting evidence or assigning guessed
  versions.
- Guarded downgrade is not a general rollback. Forward recovery is the default
  after Contract starts.

### Security, privacy, and accessibility impact

- This story adds no UI and performs no browser/CMS/provider action.
- Admin/Internal content metadata remains authenticated, authorized, audited,
  and absent from public database/API surfaces.
- Raw prompts, AI input/output, source packets, Rakuten review bodies, personal
  data, secrets, finance inputs, and production rows are not fixture or contract
  payloads.
- Media contracts preserve provenance, licensing, decorative semantics, alt
  text, and long-description references. Actual UI/accessibility behavior
  remains owned by later implementation stories.
- Publication and CMS writes remain impossible without an explicit human gate
  in their owning stories.

## 8. Risks and decisions

- ST-0003 can change while final review is active. ST-0004 must pin the final
  frozen manifest, reject later drift, and never silently update its predecessor
  hash.
- The RAOS_06 package embeds upstream copies and proposal patches. The builder
  adopts only the content-native approved contract corpus, verifies proposal
  byte equality, and does not duplicate embedded RAOS_01 through RAOS_05
  upstream documents into the v0.4 contract tree.
- Proposal SQL uses convenience constructs and omits full drift, lock, ACL,
  backfill, and rollback behavior. Formal migrations are written against the
  live predecessor shape and tested independently; the proposal is never copied
  or executed.
- Existing v0.3 ArticleVersion, Claim, Review, Publication, and AI concepts may
  overlap proposed names. New schemas/resources extend canonical concepts and
  compatibility tests forbid parallel incompatible replacements.
- Frozen schema IDs/hashes conflict with in-place enrichment. Versioned
  adoption wrappers preserve the source bytes while exposing canonical v0.4
  resource/request contracts.
- The API proposal does not define an event delta. Zero new events is the safe
  decision; application stories may add events only after a consumer contract
  exists.
- A passing local PostgreSQL 18.x run is not PostgreSQL 18.4 CI evidence. Exact
  server version is recorded and formal `TST-008` remains `NOT_EXECUTED` until
  its required environment runs.
- Implementing language types, loaders, validators, renderers, services, CMS
  adapters, or publication commands here would cross story ownership, so the
  revision stops at portable contracts, SQL payloads, fixtures, and tests.
