# ST-0107 ExecPlan — Pull-request governance

## 1. Story and outcome

- Story: `ST-0107`, `EPIC-01`, P0/S, MVP.
- Objective: install a reviewable CODEOWNERS candidate, pull-request template,
  and default-branch ruleset desired state.
- Dependency: `ST-0106`.
- Design references: `RAOS-CODEX-001` and `RAOS-SEC-001`.
- Security controls: `SEC-SDLC-001`, `SEC-SDLC-002`, and `SEC-SDLC-010`.
- Required suite: `TST-001` in the canonical CI environment.
- Acceptance criterion: changes to contract, migration, and security paths have
  an eligible owner and cannot merge without the intended code-owner review.

The local outcome is a deterministic, reviewable governance candidate. It is
not a GitHub API payload and does not apply a ruleset. The canonical `@raos/*`
team handles are unverified placeholders until the real repository, visible
teams with explicit write access, default branch, and required-check source
identities have been authenticated. Remote application and formal TST-001
remain `NOT_EXECUTED`.

## 2. Six-item preflight

1. **Story and objective:** implement only ST-0107's CODEOWNERS, PR-template,
   and ruleset desired-state boundary after the local ST-0106 predecessor.
2. **Files and contracts read:** root and canonical `AGENTS.md`; integration
   design; ST-0107 backlog row; Codex handbook; security design and
   `SEC-SDLC-001`/`SEC-SDLC-002`/`SEC-SDLC-010`; TST-001; canonical CODEOWNERS and PR-template
   examples; ST-0106 workflow/job names; the ST-0201 `Database` and ST-0202
   `Storage` follow-on jobs; ST-0005 status authority boundary.
3. **Ambiguities and safe defaults:** the GitHub repository, default branch,
   team existence/visibility/write access, numeric team IDs, required-check
   GitHub App IDs, inherited organization rulesets, and effective bypass actors
   are unknown. The safe default is a non-applicable local candidate with every
   remote mutation forbidden.
4. **Planned files:** one source contract, one deterministic generator, local
   CODEOWNERS and PR-template outputs, one non-API ruleset-policy candidate,
   one generated manifest, isolated ST-0107 tests, and story documentation.
5. **Tests:** source/schema validation; deterministic generation and no-write
   drift check; CODEOWNERS ordering/coverage; PR-template policy; ruleset
   fail-closed semantics; malicious or incomplete source fixtures; protected
   input hashes; affected static/status checks. Live PR probes are recorded as
   pending, not simulated as formal evidence.
6. **Out of scope:** creating or changing a GitHub ruleset; granting team
   access; inventing numeric bindings; enabling an ST-0005 `APPLY` transition;
   deployment/OIDC/release governance; provider credentials; publication; and
   any production or external write.

## 3. Context and official-source snapshot

The canonical CODEOWNERS example supplies the proposed `@raos/*` role map, but
also says those handles must be replaced with real teams before enforcement.
GitHub's official documentation was checked on 2026-08-02 and is recorded in
`docs/architecture/ST-0107-github-governance-snapshot.yaml`. The REST examples
use `X-GitHub-Api-Version: 2026-03-10`.

The reviewed GitHub behavior affects the implementation in four ways:

- CODEOWNERS is resolved from the pull request's base branch. The `.github/`
  location has precedence, and listed users or teams need explicit write
  access; a team must also be visible.
- Requiring code-owner review accepts an approval from any owner on a matching
  line. Multiple teams on one line are eligible alternatives, not an all-team
  quorum. The live human review must confirm that this implements the intended
  contract/migration/security/deployment owner policy.
- Active rules may be layered at repository and organization level. A local
  policy cannot prove the effective target, bypass set, or enforcement state.
- A required status check must be identified from an actual successful check
  in the repository, on a recent commit, and bound to the expected GitHub App
  source. A matching display name alone is insufficient.

## 4. Invariants

- `changes/st-0107/contracts/pr-governance.v1.yaml` is the mutable story source;
  canonical, upstream, ZIP, and earlier evidence artifacts remain immutable.
- `.github/CODEOWNERS`, `.github/PULL_REQUEST_TEMPLATE.md`,
  `changes/st-0107/ruleset-policy.v1.json`, and
  `changes/st-0107/manifest.yaml` are generated and never hand-edited.
- The generator is local and deterministic. It has no credential input,
  network access, GitHub client, or remote mutation path.
- The generated ruleset file is classified
  `DESIRED_STATE_NOT_API_PAYLOAD`. `desired_enforcement: active` states a future
  reviewed target; it does not assert current enforcement and must never be
  POSTed or PUT as-is.
- Every `@raos/*` owner remains visibly marked `UNVERIFIED_PLACEHOLDERS` until a
  live authenticated access snapshot proves the corresponding visible team's
  explicit write permission.
- The default branch is represented symbolically until the authenticated
  repository metadata identifies it.
- Every required check retains an unresolved source binding until a real check
  run identifies both its context and expected GitHub Actions integration ID.
- No bypass actor is allowed by the desired state. An authenticated read-back
  with sufficient access must prove the effective bypass set rather than rely
  on a response that may omit it.
- Required review, stale-review dismissal, last-push approval, thread
  resolution, required checks, deletion denial, force-push denial, and linear
  history remain fail closed in the desired state.
- Generated or AI-assisted work never approves itself. A distinct human review
  is required for activation and for the resulting governance evidence.
- Local generation, tests, or documentation cannot change effective canonical
  status or activate ST-0005's authoritative `APPLY` gate.
- Public/internal, finance/editorial, human approval, provenance, secret/PII,
  and no-Rakuten-review-body invariants remain unchanged; this Story adds no
  runtime application data path.

## 5. Proposed design and implementation boundary

`changes/st-0107/contracts/pr-governance.v1.yaml` maps semantic owner roles to
placeholder handles, maps owned paths to those roles, describes required PR
template disclosures, and records the future ruleset policy. The source keeps
repository-independent semantic roles separate from GitHub's future live
numeric identities.

`scripts/build_st0107_pr_governance.py` validates the source and pinned inputs,
then renders four artifacts:

1. `.github/CODEOWNERS`, including default ownership, contract/migration/
   security/deployment path coverage, explicit operations/security ownership
   of the shared Compose generator, ST-0201 PostgreSQL wrapper, ST-0202 object-
   storage wrapper and fixture, and ownership of `.github/` itself;
2. `.github/PULL_REQUEST_TEMPLATE.md`, including Story/design/control IDs,
   test/evidence and unexecuted-work fields, owner-category impact, justified
   not-applicable choices, and generated/AI-assisted human-review disclosure;
3. `changes/st-0107/ruleset-policy.v1.json`, a symbolic desired-state review
   document with no live numeric bindings and an explicit non-API
   classification; and
4. `changes/st-0107/manifest.yaml`, the source/output hash inventory and
   generation command.

Normal generation writes only those declared outputs. `--check` recomputes the
same bytes in memory, rejects drift, and writes nothing. Neither mode queries
GitHub or applies governance.

### Six live activation prerequisites

Enforcement is forbidden until one evidence pack proves all six items:

1. the authenticated repository identity and actual default branch;
2. every owner binding resolves to an actual visible team with explicit write
   permission, with reviewed stable numeric bindings;
3. every required-check context has run successfully in that repository and is
   bound to the expected GitHub Actions App/source ID;
4. an authenticated effective-rules snapshot includes parent rulesets and is
   obtained with enough access to expose the complete bypass-actor state;
5. post-application PR/direct-push probes demonstrate contract, migration,
   security, deployment, stale-review, last-push, missing-check, deletion, force-push, and
   owner-coverage behavior; and
6. a distinct human reviewer approves the repository identity, bindings,
   assembled API payload, effective read-back, and probe evidence.

Only a separately approved live runbook may turn the desired state into an API
request. It must add the authenticated default branch and numeric bindings,
show a human-readable diff, apply no bypass actor, read back the effective
rules, and preserve rollback material. That activation tooling is not part of
this local generator.

## 6. Milestones

1. **Source boundary:** add the strict governance source and official-source
   snapshot with every unresolved live binding explicit.
2. **Deterministic renderer:** add the generator, generated candidates, and
   manifest; prove `--check` is byte-for-byte and no-write.
3. **Local policy tests:** add isolated positive and adversarial tests for
   source validation, path ownership, PR-template fields, desired-state rules,
   and forbidden API/live behavior.
4. **Repository regressions:** run ST-0107 plus affected static, ST-0106,
   ST-0005 generator/request, secret, and protected-input checks.
5. **Local evidence:** capture immutable files and append only a proposal
   supported by local results. Do not claim formal TST-001 or effective GitHub
   enforcement.
6. **Future activation:** after all six live prerequisites are evidenced,
   execute a separately reviewed runbook, read back the effective rules, run
   live probes, and obtain human approval. This milestone remains unexecuted in
   the local implementation.

## 7. Test plan

Local tests map to TST-001 candidate coverage only:

- parse the source and official snapshot strictly; reject unknown, missing,
  duplicate, malformed, or hash-drifted fields;
- prove generation is deterministic, manifest hashes match, and `--check`
  preserves all repository bytes and metadata under test;
- prove CODEOWNERS last-match ordering covers default, contracts, migrations,
  security controls/tools, deployment infrastructure, and `.github/`, with
  only declared role bindings;
- map migration ownership, code-owner review, last-push approval, and a live
  migration probe explicitly to independent review control `SEC-SDLC-010`;
- prove the PR template cannot omit Story/design/control IDs, tests/evidence,
  remaining unexecuted work, owner-category impact, or generated/AI-assisted
  human-review acknowledgement;
- prove the ruleset candidate targets only the symbolic default branch, has no
  bypass actors, blocks deletion/force push, requires linear history and the
  complete PR-review policy, and lists the exact ST-0106, ST-0201 `Database`,
  ST-0202 `Storage`, and status job contexts in workflow order;
- reject an API-ready or active-claim classification, literal repository or
  branch substitutions, unverified numeric IDs, unbound check sources,
  weakened review/check policy, and attempts to mutate GitHub;
- run shell/Python syntax, formatting/type/static checks and relevant ST-0106
  and ST-0005 regressions in isolated processes.

Formal TST-001 additionally requires the real GitHub environment, effective
ruleset read-back, and live probes. A local fixture, JSON parse, or generated
hash cannot substitute for that evidence.

## 8. Evidence plan

Local implementation evidence consists of source/output hashes, the generated
manifest, isolated test logs, deterministic no-write results, protected-source
hashes, secret-scan results, and independent review. Those artifacts can
support only an `IMPLEMENTED_NOT_VALIDATED` proposal.

Live validation evidence must include the six activation-prerequisite artifacts
listed above, the exact API version and sanitized request/read-back hashes,
ruleset/repository IDs, default-branch identity, expected check integration
IDs, PR probe URLs and commit SHAs, rollback instructions, and distinct human
review. Secrets, tokens, team membership details, and private response fields
must not be committed.

## 9. Risks and decisions

- **Placeholder owners:** a syntactically valid owner can be nonexistent,
  invisible, or lack explicit write access. Local syntax is never accepted as
  owner evidence.
- **Approval semantics:** multiple owners on one CODEOWNERS line are
  alternatives. Human review and path-specific probes must confirm the
  canonical acceptance intent before activation.
- **Check-name collision:** a context string can be emitted by another App, or
  both a check and commit status. Source IDs are mandatory and collision probes
  must fail closed.
- **Stale or skipped checks:** GitHub requires recent successful checks, and a
  required workflow skipped by path/branch filters can remain pending. Each
  candidate check must be observed on the relevant PR/head behavior.
- **Layered rules:** organization rulesets can change effective behavior.
  Activation compares an authenticated `includes_parents=true` view and branch
  rule view, not only the repository-local object.
- **API drift:** the recorded API version is `2026-03-10`; a later activation
  must recheck official documentation and treat any schema/semantic change as a
  reviewed source update.
- **Status-authority coupling:** ST-0107 is a prerequisite named by ST-0005,
  but this implementation deliberately does not remove that block or authorize
  `APPLY`. Any future activation is a separate reviewed status-policy change.

## 10. Progress and completion boundary

The work log records commands and results as they occur; planned checks are not
pre-marked PASS. Local completion requires deterministic artifacts, declared
tests and regressions, capture/hash evidence, and an independent audit with no
unresolved material finding.

Even after local completion, effective canonical implementation remains
unchanged and formal TST-001 remains `NOT_EXECUTED`. ST-0107 may be proposed as
`IMPLEMENTED_NOT_VALIDATED` only. `VALIDATED` requires an authenticated GitHub
activation, complete effective read-back, live negative/positive PR probes,
and distinct human approval. This Story never activates ST-0005 `APPLY`.
