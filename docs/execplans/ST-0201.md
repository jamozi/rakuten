# ST-0201 ExecPlan - Local PostgreSQL 18 service

## Story and outcome

- Story: `ST-0201`, `EPIC-02`, P0/S, MVP.
- Objective: build a reproducible local/CI database service.
- Dependency: `ST-0102`.
- Design reference: `RAOS-DATA-001`.
- Deliverables: Compose service and bounded health check.
- Acceptance criterion: exact PostgreSQL version assertion.
- Required suite: `TST-008` in the canonical CI environment.
- Security controls: `SEC-DATA-003`, `SEC-INFRA-001`, `SEC-SDLC-003`, and
  `SEC-SDLC-004`.

The local outcome is a deterministic service candidate and a safe runtime
wrapper. It is not production configuration. Docker is unavailable in the
implementation environment, so no image pull, container start, health probe,
server-version query, vulnerability scan, or formal TST-008 is claimed.

## Preflight

1. Read the exact ST-0201 canonical Story and its ST-0102 dependency.
2. Pin the canonical backlog, TST catalog/acceptance design, security catalog,
   RAOS-DATA-001 data design, architecture design, handbook, and manifest.
3. Preserve `zip/**`, `docs/canonical/**`, `docs/upstream/**`, and
   `docs/manifest.json` byte-for-byte.
4. Resolve the official PostgreSQL `18.4-bookworm` OCI index and linux/amd64
   manifest/config identities, recording the result in an architecture
   snapshot.
5. Keep passwords out of Compose values, process arguments, logs, and the
   repository; require a local file-backed Compose secret.
6. Keep the service private by default: loopback host binding, internal bridge,
   named volume, no host network, no privileged mode, and no Docker socket.

## Implementation

1. Define `changes/st-0201/contracts/local-postgres.v1.yaml` as the sole
   semantic source for image, service, runtime, security, and evidence limits.
2. Implement a strict YAML 1.2 loader and validator that rejects duplicates,
   anchors, aliases, unsafe repository URIs, ancestor symlinks, unknown fields,
   source drift, canonical Story drift, and boundary promotion.
3. Generate `docker-compose.yml` and `changes/st-0201/manifest.yaml`
   deterministically with source/generator/command provenance.
4. Install both outputs atomically with rollback; make `--check` read-only.
5. Implement `scripts/postgres_service.sh` with a fixed local Docker socket,
   fixed local project, exact-0600 secret validation, exact Compose-service,
   health/image-config/platform/version assertions, and a disposable test
   project that cannot report PASS before successful volume cleanup.
6. Test positive semantics, negative mutation cases, source/path attacks,
   atomic rollback, fake-Docker invocation and cleanup, Bash syntax, and a real
   runtime probe that skips explicitly when Docker/Compose is unavailable.
7. Integrate a dedicated `Database` pull-request job, Make targets, workspace
   marker, documentation, and ST-0107 required-check/CODEOWNERS policy, and
   include those maintained surfaces in the generated source inventory.

## Verification commands

```bash
uv run --locked --no-sync python scripts/build_st0201_postgres_service.py
uv run --locked --no-sync python scripts/build_st0201_postgres_service.py --check
bash -n scripts/postgres_service.sh
uv run --locked --no-sync pytest -q tests/st0201
```

## Completion boundary

Local generation and tests can support at most an
`IMPLEMENTED_NOT_VALIDATED / NOT_EXECUTED` proposal. A real local runtime smoke
may prove only the ST-0201 image/health/version slice. Formal TST-008 remains
`NOT_EXECUTED` until the canonical CI environment executes its complete
database baseline scope with reviewed evidence. A vulnerability scan is also
required before validation.
