# ST-0002 ExecPlan — Apply job-state canonical revision

## 1. Story and outcome

- Story ID: `ST-0002`
- Epic: `EPIC-00`
- Requirement: `FR-020`
- Canonical decision: `INT-DEC-003`
- Outcome: preserve the RAOS v0.1 packages as audit history while producing a
  versioned, installable revision bundle for the canonical ten-state Job model.
  The bundle contains an Expand–Migrate–Contract database change, revised
  Admin/Internal OpenAPI and AsyncAPI artifacts, synchronized catalogs, and
  executable state/migration tests.

Explicit non-goals:

- creating the monorepo or final `contracts/` tree (`ST-0101`, `ST-0104`);
- pinning the Python/Node toolchains or creating CI (`ST-0102`, `ST-0103`,
  `ST-0106`);
- implementing a reusable local PostgreSQL service or queue fake (`ST-0201`,
  `ST-0203`);
- implementing the migration runner/history/lock ABI (`ST-0301`);
- installing the complete IAM/OPS schema (`ST-0303`);
- implementing dispatcher, worker, lease, retry, or DLQ runtime behavior
  (`ST-1404`);
- changing a production database, publishing, or claiming release readiness.

## 3. Invariants

- Human approval, publication controls, provenance, and public/internal
  isolation remain unchanged.
- No proposal-only SQL is executed as the implementation.
- Legacy package bytes remain unchanged and auditable.
- Status migration is explicit and count-reconcilable:
  `PENDING→REQUESTED`, `READY→QUEUED`, `FAILED→FAILED_TERMINAL`.
- Old and new status writers coexist during Expand; Contract refuses remaining
  legacy rows.
- At-least-once consumers remain idempotent; a duplicate is not represented as
  an invented self-transition.
- Job attempts remain append-only; state retry never rewrites a prior attempt.
- No review body, credential, source packet, prompt, personal data, finance
  detail, or production row is added to fixtures or logs.
- No editorial/finance/public contracts are widened.

## 4. Proposed design

### Modules and ownership

- `changes/st-0002/job-state.v1.yaml` is the single source for states,
  transitions, guards, and legacy mapping.
- `changes/st-0002/database/` contains versioned migration payloads consumed by
  the future ST-0301 runner.
- `changes/st-0002/contracts/` contains generated v0.2 contract candidates
  consumed by ST-0104.
- `scripts/build_st0002_revision.py` deterministically derives contracts and
  the hash manifest from immutable inputs and the Job-state source.
- `tests/st0002/` owns story-local static, state, and PostgreSQL verification.

### Data and transaction boundaries

The formal payload is split into separately recorded checkpoints:

1. Expand DDL: add nullable columns and dual legacy/canonical constraints in a
   short metadata transaction.
2. Expand validate/index: validate after the DDL lock is released, then build
   side-by-side canonical indexes concurrently and verify their exact
   definitions.
3. Migrate batch: map legacy state and backfill `job_version=1` for at most
   1,000 rows per transaction. Repeat with an auditable checkpoint until
   `remaining_rows=0`; `SKIP LOCKED` rows remain visible for a later pass.
4. Contract prepare: add canonical NOT VALID constraints alongside Expand in a
   short transaction, cutting off legacy writers.
5. Contract validate/finalize: validate without a preceding
   `ACCESS EXCLUSIVE` lock, then use a separate short transaction for defaults,
   NOT NULL, Expand-constraint removal, and index swap.
6. Guarded downgrade: freeze writers, prove reverse mapping is lossless, and
   restore the baseline shape atomically.

No full-table constraint scan is performed while retaining a metadata
`ACCESS EXCLUSIVE` lock. Concurrent index creation remains outside a
transaction and is resumable by its unique revision name.

### API, event, and Job changes

- Admin `Job.status` and list filtering use the canonical ten-state enum.
- Admin `Job` adds `job_version`, `deadline_at`, and
  `cancel_requested_at`.
- `JobAccepted` remains `REQUESTED|QUEUED`.
- Internal OpenAPI and AsyncAPI receive version/provenance revisions but no
  wire-breaking payload change.
- The existing `.v1` Job Message remains byte-identical; it already requires
  `job_version` and optionally allows `deadline_at`.

### Migration plan

- Correct the proposal defects: set the final status default to `REQUESTED`;
  replace the actual baseline `ck_ops_job_completion`; use MIG-001/`ops.job`
  lineage rather than the proposal's incorrect MIG-002 note.
- Validate exact column defaults, constraints, and partial-index predicates on
  PostgreSQL 18.
- Guarded downgrade is allowed only for representable rows. New-only states or
  meaningful new-column values abort before mutation.

### Failure and rollback behavior

- Expand DDL is atomic; validation and concurrent-index recovery are separate
  checkpoints.
- A failed Migrate invocation rolls back only its at-most-1,000-row batch;
  committed checkpoints remain idempotent and the runner revisits every
  remaining legacy/NULL row.
- Contract prepare is atomic. Contract validation commits independently from
  the final short metadata/index transaction, and either can be retried from
  its recorded checkpoint.
- Before Contract prepare, application rollback targets the dual-compatible
  Expand state. After Contract prepare cuts off legacy writers, forward
  recovery is the safe default.
- Destructive downgrade refuses `FAILED_RETRYABLE`, `RETRY_SCHEDULED`,
  `EXPIRED`, non-default `job_version`, deadlines, or cancellation requests.
- Forward recovery re-runs the next verified phase; no lossy automatic status
  collapse is allowed.

### Security, privacy, and accessibility

This change adds no external adapter, secret, personal data, review content,
public surface, or UI. Existing role/table grants are checked for drift. A11y
is unaffected.

## 8. Risks and decisions

- The environment provides PostgreSQL 18.3 while the package names 18.4.
  Local runtime results are strong partial evidence, not formal suite
  completion.
- Spectral and the AsyncAPI parser are absent. Custom strict static checks do
  not substitute for the future CI toolchain.
- The backlog deliberately has ST-0002 precede its installers/runners. This
  story therefore owns an immutable input bundle, not hidden implementations of
  ST-0104 or ST-0301.
- `QUARANTINED→QUEUED` timestamp cleanup and expiry behavior for retry states
  remain runtime semantics for ST-1404; this story preserves the approved 16
  edges without guessing.
- The accepted cancellation check is kept as the approved design delta. The
  state machine, not this check alone, defines allowed cancellation commands.
