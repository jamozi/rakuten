# ST-0006 open-decision gate validator

This bundle implements the canonical open-decision loader and a deterministic,
fail-closed blocker report. It does not resolve a decision, approve a Gate, or
authorize a release.

## Commands

Run from the repository root:

```bash
python3 scripts/build_st0006_decision_gates.py
python3 scripts/build_st0006_decision_gates.py --check
python3 scripts/build_st0006_decision_gates.py --validate-decisions
```

The default command verifies the complete ST-0001 import, checks the pinned
canonical inputs, validates exact YAML/CSV parity, and replaces only this
Story's generated files after a complete sibling-staged build. `--check`
regenerates into a temporary bundle and compares every generated byte.
`--validate-decisions` performs the input and blocker evaluation without
writing.

Each mode emits exactly one JSON object. `command_status: PASS` means that the
requested validation or generation operation completed; it is deliberately
separate from `open_decision_check: BLOCKED`. `status: EVALUATED` is not a Gate
PASS, and `release_authorized` is always false in this component. Exit zero
therefore reports command health, not release permission. Live enforcement is
owned by later governance Stories and must consume the explicit blocker field.

## Decision policy

`RAOS_07_open_decisions_v1.0.yaml` is the decision source of truth. The master
CSV is a parity mirror and must match every field and row. `RESOLVED` is the
only status that clears a decision; `PROVISIONAL`,
`HUMAN_DECISION_REQUIRED`, and `EXTERNAL_EVIDENCE_REQUIRED` remain unresolved.
Unknown status values fail validation.

The source has no typed per-decision-to-Gate relationship. `required_by` is
therefore preserved as opaque context and is never parsed for Gate names. Each
unresolved decision with `blocking: true` blocks all of `GATE-0` through
`GATE-4` and `PRODUCTION_RELEASE`. This is the canonical safe-side behavior,
not an inferred business decision. The current report contains 15 decisions,
14 active blockers, and six blocked targets; OD-004 remains visible but is
nonblocking.

## Ownership

Source-owned files are this README, the generator, Story tests, ExecPlan, and
work log. The following files are generated and must not be edited directly:

- `contracts/open-decision-source.schema.json`;
- `contracts/gate-blocker-report.schema.json`;
- `contracts/decision-gate-policy.v1.yaml`;
- `gate-blocker-report.v1.yaml`;
- `manifest.yaml`.

The manifest hashes every source, pinned input, and generated payload. Pinned
YAML/CSV files are parsed and hashed from the same descriptor snapshot, then
rechecked while the manifest is assembled. The canonical schemas lock the
current 15-decision inventory, status/blocking values, exact counts, and full
six-target blocker closure. They cannot validate a fabricated all-clear or
duplicate-ID report for the pinned v1 source. The manifest
excludes itself from the generated-artifact inventory to avoid recursive
self-hashing; deterministic `--check` covers it. Ownership checks reject
partial trees, nested/unlisted directories, symlinks, special/unlisted files,
and byte/hash drift.

Installation uses pinned non-symlink directory descriptors and
descriptor-relative replacement. Any ordinary exception, including an
interrupt after new files start moving, rolls the complete generated trio back
and byte-verifies the prior tree before the staging directory is removed. If
the filesystem also fails during rollback, restoration continues best-effort;
an incomplete restoration raises a recovery-required error and deliberately
retains the sibling directory containing every backup that could not be moved.
It never silently deletes the last recovery copy. The command must still not run
concurrently with an adversarial same-UID process that has arbitrary write and
rename access to the repository; such a process can already mutate source and
output files directly. Root rebinding during the tested install window is
contained by the pinned descriptor and fails with rollback rather than
redirecting writes.

## Evidence boundary

`CLEAR` would mean only that this component found no active open-decision
blocker. It never means Gate PASS, Production Ready, or release approval. The
full immutable Gate pack belongs to ST-1607. Live status `APPLY` remains
disabled pending ST-0107 and governance; deployment remains disabled pending
its owning Stories.

Local pytest/report generation is noncanonical implementation evidence.
Formal TST-005 runs in CI and TST-032 in staging; both remain `NOT_EXECUTED`.
