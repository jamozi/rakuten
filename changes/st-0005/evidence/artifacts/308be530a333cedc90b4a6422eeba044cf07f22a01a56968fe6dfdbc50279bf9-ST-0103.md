# ST-0103 ExecPlan — Pin Node toolchain

## 1. Story and outcome

- Story: `ST-0103`, `EPIC-01`, P0/S, MVP.
- Objective: pin Node, one package manager, Next.js, and TypeScript.
- Dependency: `ST-0101`; its workspace is locally materialized and drift-free,
  while canonical effective status remains unchanged.
- Required suites: `TST-001` and `TST-006` (formal environment: CI).
- Acceptance criterion: deterministic installation from a committed lockfile.
- Outcome: an inert npm workspace with exact runtime/tool/framework versions,
  an integrity-bearing generated lock, locked commands, strict static checks,
  and a Story-local Vitest smoke suite.

Product routes, components, rendering, generated contracts/types, browser
behavior, base CI, services, providers, and deployment are explicit non-goals.

## 2. Context read

The canonical master/integration documents, decisions and Open Decisions,
ST-0103 backlog row and critical path, TST-001/TST-006 definitions and CI
environment, dependency-pinning control and threat, root/canonical
instructions, ST-0101/ST-0102 handoffs, workspace generator, and accepted
Next.js/TypeScript architecture were reviewed. ST-0103 has no attached Open
Decision, direct requirement ID, or direct design reference.

The canonical architecture selects one Next.js/TypeScript codebase for public
and administrative routes, but those routes and components belong to later
Stories. It requires the implementation-time stable package manager to be
selected and its lockfile committed. Official primary release records were
checked on 2026-08-02 and are recorded in
`docs/architecture/ST-0103-toolchain-snapshot.yaml`.

Node 24.18.1 is selected because it is the current security-patched LTS line.
Its bundled npm 11.16.0 is selected rather than adding a second package-manager
bootstrap. Next.js 16.2.12 is the stable 16.2 patch while 16.3 is preview.
TypeScript 6.0.3 is selected because the current Next.js lint stack's
`typescript-eslint` peer contract supports TypeScript below 6.1; TypeScript 7
does not yet expose the compiler API needed by that tooling. ESLint 9.39.5 is
the newest compatible 9.x patch: although `eslint-config-next` accepts ESLint
9 or later, its resolved import plugin rejects ESLint 10 under strict peer
resolution. Every direct package, including React peers, static tools,
Pyright, and test tooling, is exactly pinned. The latest stable Next.js package
still declares advisory-affected PostCSS and Sharp versions, so patched
PostCSS 8.5.25 and Sharp 0.35.3 are exact transitive security overrides rather
than weakening or suppressing the audit.

- Local static/unit evidence never becomes formal CI evidence and never applies

## 4. Proposed design

The private root package is the npm workspace and owns exact development tools.
`apps/web` owns exact Next.js, React, and React DOM runtime dependencies;
`packages/web-ui` is an inert private workspace boundary. No route or component
is scaffolded. `.node-version`, `engines`, `devEngines`, and `packageManager`
record the exact Node/npm contract.

The committed `.npmrc` fixes the registry, strict peers and engines, exact
saves, lock format, install strategy, and disabled lifecycle scripts.
`package-lock.json` is npm-generated and its full source/integrity contract is
checked independently. A live package-lock audit must report zero known
vulnerabilities before the local evidence snapshot is frozen.

Root TypeScript, ESLint flat config, Prettier, Vitest, and Pyright settings
provide local TST-001/TST-006 equivalents without adding product code. The
Story-local TypeScript tests validate the pinned runner/compiler package graph,
security overrides, and inert workspace contract under the exact runtime.
Separate local import smokes cover the selected Next.js, PostCSS, and Sharp
implementations without adding product routes or components.

`scripts/node_toolchain.sh --node ABSOLUTE_PATH --npm-cli ABSOLUTE_PATH
COMMAND` is the recorded-evidence entrypoint. It uses privileged Bash startup,
validates both exact tools before repository commands run, removes inherited
Node/npm/shell/Make controls, and accepts a fixed command vocabulary. Mutable
lock generation is separate from locked sync/check. Offline reproduction uses
a fresh temporary workspace, the hydrated fixed cache, network-disabled npm,
and an installed-tree inventory comparison.

The Node wrapper remains a Node/npm-only ABI and never invokes uv or hydrates
Python. Its Pyright and aggregate check commands require the exact `.venv` to
have been synchronized independently through the Python wrapper. Immediately
before Pyright, the Node-built-in helper fails closed unless `.venv` and its
`bin` child are physical directories and the resolved executable
`.venv/bin/python`, probed with isolated startup, identifies exact CPython
3.14.6 with that virtual-environment prefix. The validation-to-execution
boundary assumes no concurrent same-UID interpreter replacement.

Before the npm lock-check semantic backstop runs, the existing Node inventory
helper performs a deterministic, Node-built-in-only comparison of the root and
three fixed workspace manifests against their package-lock v3 entries. It
compares presence and canonical JSON values for ten supported lock-owned
identity, workspace, dependency, peer-metadata, and engine fields, then derives
the lock's `hasInstallScript` bit from the three lifecycle hook names. It
requires exactly the five npm-generated v3 top-level keys, `requires: true`,
top-level identity equal to the root manifest, object-valued package entries,
and exactly the fixed non-`node_modules` workspace locations. The fixed
manifests do not use bundle or accept dependencies, funding, platform
constraints, bins, or deprecation metadata, so the preflight rejects those
npm-normalized classes and the bundled-dependencies alias rather than guessing
their projection. npm-internal integrity/shrinkwrap fields are not public
manifest inputs and remain outside this preflight; registry integrity and
locked outcomes retain their separate existing checks. Non-lock-stored
overrides retain their exact static and outcome checks. This rejects supported
drift without registry resolution while retaining exact `npm ci --dry-run` for
subtler peer and installation semantics.

## 8. Risks and decisions

- npm is selected because it is distributed with the exact Node LTS artifact;
  implicit Corepack downloads are not an evidence path.
- PostCSS and Sharp overrides are temporary explicit security controls for the
  stable Next.js 16.2.12 dependency graph. Revisit them when a stable Next.js
  patch declares patched ranges; do not remove them merely to silence an npm
  peer or audit diagnostic.
- Install lifecycle scripts are disabled. A later Story must explicitly review
  and allow any script required by newly introduced runtime dependencies.
- npm configuration and environment inputs are broad. The trusted wrapper is
  the evidence boundary; direct npm/Make use remains a developer convenience.
- ST-0101 is locally implemented but not canonically validated. This Story can
  produce only a local implementation proposal.
- Native Windows, hosted clean-clone CI, and browser execution remain
  unexecuted; the local evidence wrapper is Linux-specific.
