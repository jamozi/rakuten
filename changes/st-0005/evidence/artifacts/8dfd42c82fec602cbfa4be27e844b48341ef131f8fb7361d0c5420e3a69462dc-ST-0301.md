# ST-0301 ExecPlan - Migration framework

## 1. Story and outcome

- Story: `ST-0301`, `EPIC-03`, P0/L, MVP, multiple PRs permitted.
- Outcome: an empty PostgreSQL 18.4 database reaches one exact Alembic
  framework head through a fail-closed runner with per-revision transactions,
  a same-session advisory lock, and append-only attempt history.
- Dependencies: `ST-0201`, `ST-0002`, `ST-0003`, and `ST-0004`. They exist as
  local candidates only; canonical status remains unchanged.
- Deliverables: migration runner and history table.
- Acceptance: zero-to-latest.
- Required suites: release-blocking `TST-008` and `TST-009` in CI.

Explicit non-goals are MIG-001/domain schemas, roles, extensions, baseline
tables, ORM models, provider calls, production execution, and execution of the
mixed-transaction ST-0002 through ST-0004 SQL payloads. ST-0302 and later
Stories own those schema waves. This Story checksum-binds the 18 payloads to a
future runner ABI without making them reachable from the operational CLI.

No open decision is attached to ST-0301. Safe defaults are one linear Alembic

## 3. Invariants

- `zip/**`, `docs/canonical/**`, `docs/upstream/**`, and `docs/manifest.json`
  remain byte-identical.
- Human publication approval, public projection isolation, finance/editorial
  separation, provenance, idempotency, and no review-body use remain unchanged.
- No production, staging, recovery, publish, credential, or external-provider
  action is reachable from this runner.
- Proposal/reference SQL is never copied into or applied as the framework head.
- The exact 13 future RAOS domain schemas remain absent after ST-0301.
- Alembic version movement, revision DDL, and `SUCCEEDED` history commit in the
  same transaction; each ordinary revision has its own transaction.
- One fixed session advisory lock is held on the same physical connection
  across every version operation and released in `finally` or by session loss.
- The lock holder's DBAPI object and PostgreSQL backend PID are fixed; an
  invalidated or replacement connection cannot append history or unlock.
- History is append-only: update, delete, and truncate fail even for the normal
  migration owner.
- SQL, raw exceptions, passwords, connection URLs, host/database identity, and
  credential paths never enter diagnostics or history.
- Every source and deferred checkpoint is verified before a connection factory
  is called. Checkpoints are never concatenated or executed by this Story.
- Repeated upgrade at head is a no-op and adds no duplicate history.

## 4. Proposed design

### Modules and ownership

- `python/raos/migrations/catalog.py` owns the immutable revision/checkpoint
  catalog and hardened offline file verification.
- `python/raos/migrations/runner.py` owns target validation, connection
  creation, locking, preflight, programmatic Alembic invocation, and safe
  results/errors.
- `python/raos/migrations/cli.py` owns the JSON-only `verify`, `status`, and
  `upgrade` interface.
- `migrations/env.py` accepts only an injected SQLAlchemy connection and records
  atomic success through Alembic `on_version_apply`.
- `migrations/versions/202608030001_framework_install_history.py` creates the
  public version/history ABI. `public` avoids inventing a fourteenth domain
  schema; no application or PUBLIC grants are added.
- `scripts/build_st0301_migration_framework.py` owns contract validation,
  deterministic generated catalog evidence, and the Story manifest.

### Data and transaction boundaries

`public.raos_migration_version` is Alembic's authoritative head.
`public.raos_migration_history` stores attempt ID, revision, direction, status,
source digest, runner version, exact server version, timestamp, transaction ID,
and an allowlisted static error code. It stores no connection identity or SQL.
Runner and server versions are immutable catalog values per revision, so a
future runner or PostgreSQL patch does not invalidate retained historical rows.

The root bootstrap cannot commit `STARTED` or `FAILED` before its history table
exists; its `SUCCEEDED` row is inserted by `on_version_apply` in the root
revision transaction. Future revisions first commit `STARTED`, atomically
commit `SUCCEEDED` with version movement, and append `FAILED` only after the
failed revision rolls back. A later lock holder closes an unterminated attempt
with `INTERRUPTED_BEFORE_TERMINAL` before retrying.

The runner builds a `postgresql+psycopg` `NullPool` engine from explicit
host/port/database/user and an owner-only mode-0600 non-symlink password file.
Only an absolute Unix-socket directory or loopback literal is accepted. Ambient
`PG*` settings, DSNs, URL userinfo, arbitrary options, and production are
rejected. The secret is read once into memory and never rendered.

### Migration and lock plan

The production graph has one root/head revision. The runner rejects multiple
heads, branches, unknown revisions, unmanaged non-empty databases, stamp,
autogenerate, offline SQL, arbitrary targets, and downgrade below the retained
history anchor. Failure leaves version and revision DDL unchanged; after the
blocking condition is corrected, the same explicit upgrade performs forward
recovery.

The advisory key is the signed big-endian first eight bytes of
`SHA-256("jp.raos.migration.framework.v1")`, equal to
`-4304770990298879982`. `pg_try_advisory_lock` fails immediately on contention;
the runner never waits, force-unlocks, terminates another backend, replaces the
connection, or retries transparently.

The 18 prior SQL files are verified as regular non-symlink files with exact
hashes. Verification order is numeric; executable plans are separately defined
as forward `001-005,007-011,013-017` and guarded reverse `018,012,006`. Both
execution plans remain disabled until the owning MIG waves translate and
activate them as Alembic revisions.

### API, event, job, security, privacy, accessibility

There is no API, event, job, UI, accessibility, content, personal-data, or
provider change. CLI output is a deterministic allowlist. Errors contain only
static codes/messages. PUBLIC receives no version/history table privileges,
and the mutation-rejection function is not PUBLIC-executable.

stale provider data, duplicate messages, and public APIs are not applicable

## 8. Risks and decisions

- Decision: one necessary production root revision, not an artificial second
  head. Future wave revisions supply previous-to-latest paths.
- Decision: public metadata tables, not a new RAOS schema or later-owned `ops`.
- Decision: explicit constrained target/password file, not ambient libpq config
  or a DSN.
- Decision: verify but do not execute the 18 mixed-transaction checkpoints.
- Risk: no exact PostgreSQL 18.4 binary is currently available. Use 18.3 only
  for clearly labeled partial runtime evidence; do not weaken the exact check.
- Risk: changing `pyproject.toml`/`uv.lock` drifts ST-0204's source manifest.
  Regenerate generated manifests after source freeze and preserve historical
  evidence/request files unchanged.
- Risk: the workspace is not a valid Git repository, so PR and independent
  owner-review evidence cannot be created locally. Report it as unexecuted.
