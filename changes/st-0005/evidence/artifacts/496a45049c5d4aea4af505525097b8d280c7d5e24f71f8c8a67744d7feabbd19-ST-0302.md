# ST-0302 ExecPlan - Foundation schemas and extensions

## 1. Story and outcome

- Story: `ST-0302`, `EPIC-03`, P0/M, MVP, one PR preferred.
- Outcome: the reviewed ST-0301 Alembic graph advances to one foundation head
  that creates empty `ops` and `iam` schemas, establishes the PostgreSQL
  built-in type/extension policy, and proves PostgreSQL 18 UUIDv7 behavior.
- Dependency: `ST-0301`; its local candidate and exact PostgreSQL 18.4 harness

Explicit non-goals are IAM, Job, Outbox, Inbox, Audit, Object Artifact, roles,
grants to workload roles, seeds, ORM models, and all other domain schemas or

## 4. Proposed design

### Modules and ownership

- A second Alembic revision creates/comments/revokes PUBLIC access to `ops`
  and `iam`; its reversible downgrade drops them with `RESTRICT`.
- The revision catalog advances to `202608030002` with immutable source hash,
  runner version 1.1.0, story ID, and exact server version 180004.
- The migration runner validates schema owner/comment/ACL, absence of
  ST-0303 objects and extension dependencies, and built-in UUIDv7 behavior.
- The existing command surface gains a one-step `downgrade`; arbitrary targets
  and movement below the retained anchor remain unavailable.
- `scripts/build_st0302_foundation.py` is the sole writer for the revision,
  validation SQL, generated Story catalog, and manifest.

### Data and transaction boundaries

There is no application row data. Schema creation, Alembic version movement,
and `SUCCEEDED` history are one transaction. `STARTED` is committed before a
non-root operation; failure rolls back DDL/version and appends a sanitized
`FAILED` event while retaining the same advisory-lock session.

The one-step downgrade records `DOWNGRADE` history against the revision being
removed. Its two `DROP SCHEMA ... RESTRICT` statements share one transaction,
so an unexpected object leaves both schemas and the head intact. A later
upgrade is a supported forward-recovery path.

### Validation and security

The generated SQL checks exact server 18.4, exact schema metadata and owner,
owner `CREATE`/`USAGE`, absence of non-owner and namespace default ACLs, no
relations/routines/custom types, only the default `plpgsql` extension,
resolution of the declared `pg_catalog` built-in types, UUIDv7 return
type/version/timestamp extraction, and one exact clean three-event migration
history whose terminal transaction matches the sole version row. It contains
no dynamic SQL or input.

There is no API, event, job, UI, accessibility, provider, personal-data, or
content change. No workload grants are invented before ST-0306.

## 8. Risks and decisions

- Decision: create only `ops` and `iam`; copying all 13 upstream schemas or
  any table would violate the canonical Story split.
- Decision: zero extension/custom-type DDL; the upstream baseline explicitly
  depends on PostgreSQL built-ins and creates neither.
- Decision: make one-step downgrade operational through the reviewed runner,
  while refusing arbitrary targets and the history anchor.
- Decision: use `RESTRICT`, not `CASCADE`, so later-owned or unexpected objects
  cannot be destroyed.
- Decision: fail closed on owner privilege removal and namespace default ACLs;
  ST-0306 must update this revision-aware validation when grants become owned.
- Decision: keep the content-addressed ST-0301 manifest immutable. Its legacy
  entrypoint delegates to the active cumulative ST-0302 generator, avoiding a
  recursive predecessor-manifest rewrite.
- Risk: the workspace has no valid Git repository, so formal PR/owner approval
  cannot be produced locally.
